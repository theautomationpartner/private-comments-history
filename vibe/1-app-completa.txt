--- Conversión de fechas: usar SIEMPRE `value`, NUNCA `text` ---

Esto es crítico y está verificado contra la API de monday. En una columna de tipo date:

  value  ->  {"date":"2026-07-27","time":"08:05:08"}   <- UTC real
  text   ->  "2026-07-27 05:05"                        <- YA convertido al huso de quien consulta,
                                                          y sin ningún indicador de zona

Si se usa `text`, new Date() lo interpreta como hora local del navegador y el desfasaje se aplica
DOS VECES. En este caso concreto eran 6 horas de error, en una app cuyo sentido son las fechas.
Los campos `... on DateValue { date time }` tienen el mismo problema que `text`.

⚠️ Y hay un segundo caso: la columna puede traer FECHA SIN HORA. Eso no es un instante, es un día
calendario. Si se lo trata como medianoche UTC y después se pasa a hora local, se corre al día
ANTERIOR en cualquier huso al oeste de Greenwich — el mismo síntoma que veníamos evitando, por
otra puerta. Por eso la función devuelve además un flag, y se usa mediodía como hora neutra:

function fechaDeColumna(rawValue) {
  if (!rawValue) return null;
  try {
    const { date, time } = JSON.parse(rawValue) || {};
    if (!date) return null;
    // mediodía, no medianoche: así no se corre de día en ningún huso entre UTC-11 y UTC+11,
    // que cubre de sobra a los usuarios de esta app (Israel) y a quien la desarrolla (Argentina)
    return { iso: `${date}T${time || "12:00:00"}Z`, tieneHora: Boolean(time) };
  } catch {
    return null;
  }
}

El board de historial acumula UNA entrada por cada cambio de CADA una de las 5 columnas de TODOS
los proyectos: es el board que más crece del sistema. Si se usa un `limit` fijo sin paginar, los
proyectos cuyas entradas caigan fuera de esa primera página muestran "No entries yet" — o sea, la

en la primera llamada.

Hay que repetir la consulta pasando el `cursor` que devolvió la anterior, acumulando los `items`,
hasta que `cursor` venga null. Poner un tope de 20 páginas como red contra un bucle infinito.

⚠️ Esto es paginación INTERNA para juntar todos los datos. NO es paginación en la pantalla: el
usuario nunca ve botones de "página siguiente" (ver la lista de cosas que NO hacer).

Reglas de las páginas — cada caso tiene una respuesta distinta y NINGUNA es "mostrar lo que junté":

  · `boards` vacío en la PRIMERA página          -> SIN ACCESO (el usuario no está suscripto)
  · `boards` vacío en una página POSTERIOR       -> ERROR REAL (ya sabemos que tiene acceso; ni
                                                    mentirle con el cartel de privacidad, ni
                                                    mostrarle datos incompletos)
  · `items_page` null pero el board existe       -> esa página trajo cero filas: cortar la
                                                    paginación y seguir con lo acumulado.
                                                    NO es sin acceso ni error.
  · se llega a las 20 páginas y `cursor` sigue
    sin ser null                                 -> ERROR REAL. Mostrar los datos parciales sería
                                                    exactamente el bug que esta paginación viene a
                                                    arreglar, solo que con 10.000 entradas.
