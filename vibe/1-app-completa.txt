===============================================================================
QUÉ ES LA APP
===============================================================================

Las columnas de texto de monday se reemplazan en cada edición: no guardan versiones. Un board de
proyectos tiene 5 columnas de texto donde el equipo escribe seguimiento, y una automatización de
monday va guardando cada cambio como un ítem nuevo en un board privado de historial.

Esta app se abre dentro de un proyecto y muestra ese historial, separado por columna de origen.
La app NO genera el historial: solo lo lee. La automatización ya existe y ya está funcionando.

--- Conversión de fechas: usar SIEMPRE `value`, NUNCA `text` ---

Esto es crítico y está verificado contra la API de monday. En una columna de tipo date:

  value  ->  {"date":"2026-07-27","time":"08:05:08"}   <- UTC real
  text   ->  "2026-07-27 05:05"                        <- YA convertido al huso de quien consulta,
                                                          y sin ningún indicador de zona

Si se usa `text`, new Date() lo interpreta como hora local del navegador y el desfasaje se aplica
DOS VECES. En este caso concreto eran 6 horas de error, en una app cuyo sentido son las fechas.
Los campos `... on DateValue { date time }` tienen el mismo problema que `text`.

function toUtcIso(rawValue) {
  if (!rawValue) return null;
  try {
    const { date, time } = JSON.parse(rawValue) || {};
    return date ? `${date}T${time || "00:00:00"}Z` : null;
  } catch {
    return null;
  }
}

--- Consulta principal: HAY QUE PAGINAR CON CURSOR ---

El board de historial acumula UNA entrada por cada cambio de CADA una de las 5 columnas de TODOS
los proyectos: es el board que más crece del sistema. Si se usa un `limit` fijo sin paginar, los
proyectos cuyas entradas caigan fuera de esa primera página muestran "No entries yet" — o sea, la
app MIENTE y no aparece ningún error. Ya pasó: con 209 entradas y limit 200, 9 quedaban invisibles.

query ($board: ID!, $cols: [String!], $cursor: String) {
  boards(ids: [$board]) {
    items_page(limit: 500, cursor: $cursor) {
      cursor
      items {
        id
        created_at
        column_values(ids: $cols) {
          id
          text
          value
          ... on BoardRelationValue { linked_item_ids }
        }
      }
    }
  }
}

Variables: board = BOARD_HISTORIAL, cols = los 5 column_id de la tabla de arriba, cursor = null
en la primera llamada.

Hay que repetir la consulta pasando el `cursor` que devolvió la anterior, acumulando los `items`,
hasta que `cursor` venga null. Poner un tope de 20 páginas como red contra un bucle infinito.

⚠️ Esto es paginación INTERNA para juntar todos los datos. NO es paginación en la pantalla: el

--- Procesamiento (transcribir tal cual) ---

const val = (cvs, id) => cvs.find((c) => c.id === id) || {};

// IMPORTANTE: hay TRES situaciones distintas y monday responde 200 en todas. Distinguirlas en
// este orden exacto:
//
//   1) la promesa rechaza, O la respuesta trae `errors`   -> ERROR REAL ("Something went wrong")
//      (monday devuelve 200 con { data: null, errors: [...] } ante una query inválida o un límite
//       de complejidad; si eso se confunde con lo de abajo, se le muestra "no tenés permiso" a
//       alguien que sí tiene permiso)
//   2) `data.boards` es una lista VACÍA                    -> SIN ACCESO ("This information is private")
//      (es como monday responde cuando el usuario no está suscripto al board privado)
//   3) el board vino pero no hay entradas de este ítem     -> SIN ENTRADAS ("No entries yet")
//
// Si `items_page` viene null pero el board existe, tratarlo como lista vacía, NO como error.

if (respuesta?.errors) { /* ERROR REAL */ }
const board = respuesta?.data?.boards?.[0];
if (!board) { /* SIN ACCESO */ }

const rows = /* todos los items acumulados de todas las páginas */;

// Primero se filtran las filas de ESTE ítem. Todo lo que venga después tiene que salir de acá:
// `rows` es el board entero, y usarlo por error trae datos de otros proyectos.
const filas = rows.filter((r) => {
  const link = val(r.column_values, COLS.linkedItem);
  return (link.linked_item_ids || []).map(String).includes(String(itemId));
});

const entries = filas
  .map((r) => {
    // si la entrada tiene fecha propia se usa esa; si no, la de creación del ítem
    const original = toUtcIso(val(r.column_values, COLS.originalTimestamp).value);
    return {
      id: r.id,
      text: val(r.column_values, COLS.commentText).text || "",
      createdAt: original || r.created_at,
      sourceColumn: (val(r.column_values, COLS.sourceColumn).text || "").trim(),
    };
  })
  // las entradas sin texto se descartan: son eventos de "se vació la columna"
  .filter((e) => e.text.trim())
  // de la más nueva a la más vieja. El desempate por id evita que dos entradas del mismo segundo
  // (o del mismo día, si la fecha guardada no trae hora) salgan en distinto orden en cada carga.
  .sort((a, b) => new Date(b.createdAt) - new Date(a.createdAt) || Number(b.id) - Number(a.id));

// Nombre del proyecto: si el proyecto fue borrado su nombre ya no se puede consultar, pero quedó
// guardado en la columna Source Item de cada entrada. Se usa como respaldo.
// ⚠️ Sale de `filas` (las de ESTE ítem), NUNCA de `rows` (el board entero): con `rows[0]` se
// mostraría el nombre del primer proyecto que devuelva la API, que casi siempre es otro.
const nombreDeRespaldo = val(filas[0]?.column_values || [], COLS.sourceItem).text;
const nombreDelProyecto = nombreConsultado || nombreDeRespaldo || "";

// Solo para el texto del cartel de privacidad, NO es la medida de seguridad.
// Si el contexto no trae el email (pasa en algunas versiones), pedirlo con: query { me { email } }
// Si aun así no se consigue, tratar isOwner como false: se muestra el texto neutro.
const isOwner = (contexto.user?.email || "").toLowerCase() === OWNER_EMAIL.toLowerCase();

   en negrita y con un fondo suave. Todas son clickeables y accesibles con el teclado.

   FEED: título "History" y debajo las tarjetas, en LÍNEA DE TIEMPO: a la izquierda de cada
   tarjeta hay un punto violeta, y una línea vertical fina que conecta un punto con el siguiente
   (la última tarjeta no lleva línea hacia abajo). Cada tarjeta contiene:
     - una fila con un ícono de calendario + la fecha, y un ícono de reloj + la hora
     - debajo, el texto del comentario, respetando los saltos de línea

   FORMATO DE FECHA Y HORA — leer completo, acá es fácil equivocarse por horas.

   El dato guardado es un instante en UTC (por eso se usa `value` y no `text`). Ese instante se
   muestra en la HORA LOCAL DE QUIEN MIRA, usando toLocaleDateString / toLocaleTimeString con
   locale "en-US" y SIN pasar `timeZone`:

     new Date("2026-07-27T08:05:08Z").toLocaleDateString("en-US",
       { month: "long", day: "numeric", year: "numeric" })   ->  "July 27, 2026"
     new Date("2026-07-27T08:05:08Z").toLocaleTimeString("en-US",
       { hour: "numeric", minute: "2-digit" })               ->  "5:05 AM" en Argentina (UTC-3)
                                                                 "11:05 AM" en Israel (UTC+3)

   Es correcto y buscado que dos personas en husos distintos vean horas distintas: cada una ve la
   hora que era PARA ELLA. Lo que NO puede pasar es que el desfase se aplique dos veces, y eso es
   lo que ocurre si se parte de `text` en vez de `value`.

   Los usuarios de esta app están en Israel; quien la desarrolla, en Argentina. Si al comparar
   contra monday las horas dan corridas exactamente 3 o 6 horas, se usó `text`.
